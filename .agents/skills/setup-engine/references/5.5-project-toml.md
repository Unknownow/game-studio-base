# /setup-engine — Section 5.5: Populate project.toml

> Part of `/setup-engine`. `SKILL.md` names when to read this file; the settings it
> resolved and the rules under its later headings still apply here.

## 5.5 Populate `project.toml` (Primary Config Store)

**In this file:**

- 5.5.1 Build the values
- 5.5.2 Write them to `project.toml`
- 5.5.3 Verify the dual-write

`project.toml` at the repo root is the **primary** store for project configuration. The
`docs/technical-preferences.md` file written in Section 5 is the human-readable mirror. This step is
a **dual-write** — the same engine facts go into both files, and `project.toml` wins when a skill
reads a key present in both.

### 5.5.1 Build the values

Derive every value from the engine and language already chosen in Sections 3–4.
Do NOT re-ask for the **engine, version or language** — reuse those decisions.

| Key | Value |
|---|---|
| `engine.name` | the engine's name (for example `unity`, `godot`, `unreal`; lower case) |
| `engine.version` | the version from Section 3 |
| `engine.language` | the language from Section 4 |
| `engine.rendering`, `engine.physics` | the engine's typical defaults, only when the engine's section gives them |
| `testing.command` | the command that runs the project's tests headlessly, from the engine's section |
| `commands.build`, `commands.run`, `commands.smoke` | from the engine's section; leave unset when it gives none |
| `engine.editor_path` | the executable the probe found in Section 3. Machine-specific: write it to `project.local.toml` with `--local` |

Engine step `hook: setup-engine/commands`: if `ENGINE.md` exists, follow its section `## hook: setup-engine/commands`; otherwise ask the user how their engine does this and record the answer in `ENGINE.md` under that heading.
The section gives the values above for the engine, with the shape facts each depends on (target platform,
2D or 3D). **Target platform and 2D-vs-3D are collected by Section 2 on only one of its entry paths.**
Resolve each input in this order and stop at the first that answers:

1. Section 2's answers, if that path ran.
2. The design artifact: `design/gdd/game-concept.md` at `standard` and `full`, `design/game-brief.md` at `minimal`.
3. Ask. Do not infer the shape from the engine name, and do not write a value you could not justify.
   Options: `2D · non-web` / `2D · web` / `3D · non-web` / `3D · web`, plus `Leave unset` — a legitimate
   answer here, revisited via `/settings` once the concept exists.

An unset value is better than a wrong one, because nothing downstream questions it. `engine.rendering` and
`engine.physics` are typical defaults: tell the user they can be changed later with `/settings`.

Commands whose exact form cannot be sourced for the user's platform are left unset with a note, never
written as a guessed path.

Naming conventions and the specialist routing go into `docs/technical-preferences.md` (Section 5) and the
engine's rules, not into `project.toml`.

### 5.5.2 Write the values to `project.toml`

Show the user the full set of values and ask:

> "May I write the `engine`, `testing` and `commands` values to `project.toml`?"

Wait for confirmation, then write each value with
`python tools/studio.py config-set engine.name <value>` (and the same for each other key; add `--local`
for `engine.editor_path`). `config-set` keeps the file's comments and order, creates a missing table, and
reads the value back: check each readback row. Keys `config-set` refuses (exit 5, a list or table) are
edited by hand. Do not seed `modes.review_mode` here: it is a rigor-fronted knob, and an explicit value
would shadow the rigor expansion.

If `project.toml` does not exist, create it from the template's `project.toml` first.

### 5.5.3 Verify the dual-write

Run `python tools/studio.py config --keys engine.name,engine.version,engine.language,testing.command` and
confirm the values match what was written to `docs/technical-preferences.md`. If they diverge, report the
discrepancy to the user and stop — a split config corrupts skill reads.
